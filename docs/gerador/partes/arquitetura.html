3Visão geral

É uma aplicação monolítica de servidor. Um container, um banco, um volume de mídia. Não há microsserviço, fila, cache distribuído nem API separada do front-end — e nada disso faz falta na escala real do problema: uma ONG com noventa animais e cento e cinquenta padrinhos.

Por que o banco fica fora do Docker

O servidor já mantém um PostgreSQL único no host, compartilhado com outras aplicações e com backup centralizado. Subir mais um Postgres dentro do compose significaria mais uma rotina de backup para esquecer. O custo dessa escolha é a configuração de rede descrita na seção 31.

5.1A regra de dependência

As camadas só olham para baixo. app/ chama server/, que chama lib/, que fala com o banco e o disco. Nada em lib/ importa de server/, e nada em server/ importa de app/.

Há uma consequência prática disso que já cobrou seu preço durante o desenvolvimento e vale registrar:

Armadilha: constante exportada de módulo de cliente

A paleta dos gráficos morava dentro de Graficos.tsx, que é 'use client'. Tudo que um módulo de cliente exporta vira referência de cliente — inclusive uma função pura como corDaCategoria(). Quando a página de impacto (servidora) tentou chamá-la durante o render, o Next devolveu Attempted to call corDaCategoria() from the server e a rota caiu com 500. A correção foi mover a paleta para src/lib/paleta.ts, sem diretiva: cor é dado, não componente. Vale a regra geral — constante compartilhada entre servidor e cliente nunca deve morar em arquivo marcado como cliente.

6Ciclo de vida de uma requisição

6.1Leitura — abrir uma página

Exemplo: um visitante abre /animais/thor a partir de um link recebido no WhatsApp.

  1. O Next casa a rota com (publico)/animais/[slug]/page.tsx.
  2. generateMetadata() roda primeiro e monta as tags Open Graph — título, descrição e imagem de capa. É o que o WhatsApp lê para montar o preview; sem imagem, o link vira um retângulo cinza que ninguém abre.
  3. O componente servidor chama carregarPerfilPublico(slug) em src/server/publico.ts, que faz uma consulta com include aninhado para animal, fotos, apadrinhamentos ativos, diário, atualizações públicas e campanhas, e mais três contagens em paralelo.
  4. calcularCusto() deriva a cobertura da meta a partir dos apadrinhamentos ativos já carregados — sem ida adicional ao banco.
  5. O HTML é transmitido. O único JavaScript enviado ao navegador é o do botão de compartilhar. A página inteira funciona com o JavaScript desligado.

6.2Escrita — enviar um formulário

Exemplo: a mesma pessoa confirma o apadrinhamento do Thor.

  1. O <form action={acao}> envia o FormData para a Server Action apadrinhar(). Funciona sem JavaScript; com JavaScript, useActionState acrescenta o estado de envio.
  2. A ação chama conferirMesmaOrigem() — defesa de CSRF que complementa o SameSite do cookie (seção 21).
  3. Um schema Zod valida e normaliza tudo. Nada de FormData cru alcança o banco.
  4. Regras de negócio: o padrinho é criado ou reaproveitado pelo e-mail, e a ação recusa o pedido se já houver apadrinhamento ativo daquela pessoa para aquele animal.
  5. Uma transação grava o apadrinhamento, a primeira mensalidade pendente, o evento de diário — se for o primeiro padrinho do animal — e a notificação.
  6. A auditoria é registrada fora da transação: ela não pode derrubar a operação, mas também não pode falhar em silêncio.
  7. A ação devolve um estado tipado; a tela troca o formulário pela confirmação com a chave PIX.

Doze arquivos actions.ts seguem essa mesma sequência. Quando houver dúvida sobre onde acrescentar uma regra, é essa ordem que ela deve respeitar: origem, validação, regra, transação, auditoria, revalidação.
